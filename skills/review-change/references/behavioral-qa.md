# Independent QA

- Derive a behavior matrix from authoritative criteria before reading developer or senior verdicts: relevant input classes, transitions, boundaries, negative cases and observable effects. For each criterion, state the expected result taken from its text and at least one hypothesis of how the change could fail it.
- Walk the risk grid and account for every class as tested (result), not applicable (reason) or not tested (obstacle): user input (bounds, empty, invalid), network call (error, timeout, empty response), persistent state (reload, back navigation, double submit), asynchronous work (ordering, cancellation), data or migration (existing data, rollback), permissions (unauthorised role), observable security (data exposed or action allowed without the right), accessibility in behavior (keyboard path, focus, accessible name). A class the change does not touch is not applicable; do not pad it with scenarios.
- From the diff, list the consumers of modified symbols and run one smoke check per neighbouring flow they belong to. Inspect the implementation and tests for missing scenarios independently of the author's coverage map.
- Verify the final code after corrections have stopped, in order of risk: criteria observations and executed break attempts first, at least one attempt per acceptance criterion, then the general gates, rerun or reused from a result on the same code snapshot. An attempt only read from the code does not count toward that floor. General gates and acceptance checks answer different questions.
- When the caller provides a disposable worktree, which it does when the diff touches test files, probe the new or changed tests there: with the fix reverted or the defect reinjected they must go red, and a test that stays green proves nothing. Without a worktree this probe is not applicable. Never modify the delivered checkout for a counterexample.
- Rerun new or changed tests and any failure a few times from a clean state before concluding. Report a result that changes between runs or with test order as unstable, with the runs.
- Reuse a validated setup recipe to reach the state, but inspect whether its fixtures mask behavior or impose the answer. Say for each observation whether it ran against the real backend or a stub, and distinguish product failures from malformed test setup.
- Confirm author evidence only after checking what it actually establishes, its version and its scope. Label confirmation separately from fresh execution, and retain an independent counterexample search even when the author reports all green.
- Keep failure cause separate from result. A pre-existing failure requires the same failure on the base ref in the worktree, not an assertion from another report; without a worktree the failure counts against the change. Where fresh execution is impossible, report the exact gap and evidence still available.
- Return a result per criterion, every break attempt with its hypothesis, trigger, expected and observed result, and the scenarios left untested with their obstacle. A convincing explanation does not close an unverified check.
