Implementation Harness

Comment fonctionne le harnais

Une console locale qui lance le vrai binaire claude sur un ticket GitLab et rend visible ce qu’il fait. Aucun appel direct à l’API, aucune clé : tout passe par la session Claude Code et ses hooks.

1. Le trajet d’un run

Tu colles l’URL d’un ticket, le serveur retrouve le dépôt, crée un worktree git pour ce run et y ouvre une session Claude Code dans un PTY. Le checkout principal n’est pas touché. Chaque hook de la session revient au serveur, qui met à jour l’état du run et le pousse à l’interface. Une question du workflow bloque la session jusqu’à ta réponse.

flux du run (hooks, événements, état) question, réponse ou décision, c’est à toi documents produits par une session enchaînement simple prévu, pas commencé
Ce que reçoit le worktreeLes dossiers de dépendances ignorés par Git, copiés ou liés depuis le checkout principal, et les fichiers .env*. Pas les sorties de build.
Si le worktree ne peut pas être crééLe run ne démarre pas. Le serveur ne se rabat jamais sur le checkout principal.
Après la sessionSupprimé quand le run est terminé, la MR ouverte hors draft, les preuves archivées, l’arbre propre et la branche poussée. Sinon conservé avec sa raison. La branche n’est jamais supprimée.

2. Le workflow /implementation-harness:implement

Dix étapes, conduites par un pilote qui délègue à des agents spécialisés. La seule étape interactive est la deuxième. Chaque étape laisse des fichiers dans .claude/tasks/, que la console archive et affiche.

  1. 01

    Lire le ticket

    Le ticket et tous les documents liés.

  2. 02 · à toi

    Questions

    Seule étape interactive. Le pilote écrit ensuite le registre des critères, avec des identifiants stables AC1, AC2…

    acceptance-criteria.json
  3. 03

    Branche dédiée

    Créée dans le worktree du run, depuis la branche de base choisie.

  4. 04

    Plan et découpage

    ticket-planner sur un ticket complexe, le pilote seul sur un ticket simple. Chaque tâche cite ses critères.

    planner-output.json
  5. 05

    Implémentation

    Une tâche à la fois, par des agents developer, puis fusion de leurs rapports et appel nominal contre le plan.

    developer-report-<id>.md, dev-evidence.json
  6. 06

    App joignable et mesures

    Le changement est mesuré dans l’application qui tourne, sur du code figé.

    state.json, captures
  7. 07

    Mise à l’épreuve

    Revues indépendantes, dimensionnées selon la taille du diff (détail ci-dessous).

    senior-review.md, qa-report.md, designer-review.md
  8. 08

    Merge request

    Description préparée depuis la synthèse des preuves. Les critères en échec ou non vérifiés y restent visibles.

    acceptance-summary.md
  9. 09

    Revue consolidée

    Un commentaire de revue publié sur la MR, avec les captures.

    review-summary.md (niveau 2)
  10. 10

    Rapport final

    Résumé dans le terminal, fin déclarée, archive synchronisée, puis nettoyage.

    workflow-state.json

3. La santé d’un run

Le serveur ne se fie pas au silence. Il lit des signaux précis, les évalue à chaque tick et ouvre un incident quand quelque chose demande une décision. Une action sur un incident est enregistrée avant d’être exécutée.

suspected_stallLe silence seul n’est qu’un doute. Une fin de tour en plein workflow ne suffit plus à réclamer ton attention.
failed + lost_sessionLa session s’arrête avant d’avoir déclaré un résultat. Le run est interrompu, pas en erreur de workflow.
Hooks perdusemit.mjs réessaie une fois, puis met l’événement en attente dans hooks-spool.jsonl, rejoué au hook suivant et à chaque tick.

4. La boucle d’auto-amélioration

Le harnais travaille aussi sur son propre dépôt, une amélioration à la fois. Rien n’est poussé ni mergé tout seul : le bouton de merge de l’interface est la seule voie de promotion. Un merge qui touche console/ ou bin/ demande un impl restart.

5. Un lot de tickets

Tu colles plusieurs URL d’un coup. Pour chaque dépôt, une session d’analyse prédit ce que chaque ticket toucherait et relie ceux qui ne peuvent pas tourner ensemble. Le serveur lance ce qui n’est en conflit avec rien, 3 runs à la fois au plus, et retient les autres jusqu’à ce que la MR attendue soit mergée.

Ce que coûte l’analyseUne session Claude Code sur Sonnet par dépôt et par lot, 5 minutes au plus par défaut. Elle ne prend aucune des 3 places.
La veille ne coûte aucun tokenC’est le serveur qui appelle glab api, seulement tant qu’un ticket attend une MR. Si GitLab ne répond pas, le ticket reste retenu.
Analyse en échec ou peu fiableFichier absent ou refusé, délai dépassé, ticket trop vague : les tickets de ce dépôt passent un par un.
DérogationDepuis la base : la seconde MR devra sans doute être reprise à la main. Empilé : la MR cible la branche de l’autre ticket et se merge après elle.
LimitePas encore exercé sur une vraie instance GitLab : les tests remplacent claude et glab par des simulateurs.
