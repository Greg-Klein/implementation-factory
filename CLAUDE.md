# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Two things in one repo:

1. **A Claude Code plugin** (`.claude-plugin/`, `commands/`, `agents/`, `hooks/`, `skills/`). `/implementation-factory:implement` drives a GitLab or GitHub ticket end to end (clarify, plan, implement, test, specialized reviews, MR or PR). The ticket URL decides the forge: `glab` and the `glab-gitlab-api` skill for GitLab, `gh` and the `gh-github-api` skill for GitHub, where the ticket status is never moved and review captures are attached with `gh --attach` when the installed `gh` has it (2.99.0 or later), kept local otherwise. `improve` and `rebase` run the self-improvement loop on this repo itself, and `judge-improvement` is run headless by the console to decide whether a finished improvement branch is merged without the user; `review` is the review step. `schedule` is run headless by the console to compare the tickets of a batch (agent `ticket-scheduler`, files defined in `contracts/schedule.md`).
2. **A local console** (`console/`): a Next.js UI plus a Node server that spawns the real `claude` binary in a PTY (`claude --plugin-dir <this repo> "/implementation-factory:implement <ticket>"`), inside a git worktree of the target repository created for that run, and makes its progress, agents, questions and documents visible. No direct Anthropic API calls, no API key.

There is no desktop app. The console only runs from the checkout through `impl`, so a merged self-improvement lands in the code that serves it (plugin files on the next run, `console/` and `bin/` after `impl restart`, which the merge notice asks for, or which the console runs itself once idle when the automatic merge is on).

`bin/implementation-factory` is the `impl` launcher (start/demo/restart/stop/status/config/improve). It starts the server in the background (`nohup`, output in `<data dir>/server.log`) and returns once `/api/runs` answers. Every other command it accepts (`client_commands`: `run`, `runs`, `show`, `watch`, `attach`, `answer`, ...) is handed to the terminal client, `console/cli/index.ts` run with `tsx` from the caller's directory, with `IMPL_CONSOLE_URL` (the local server unless the shell names another) and `IMPL_PROGRAM`. Only `run` starts a server when none listens, without the browser; a reading command never does. `bin/config.mjs` + `env-schema.mjs` + `env-file.mjs` implement `impl config` over a local `.env` (the shell environment wins over `.env`, which wins over the defaults, see `.env.example`).

## Commands

All from `console/` (Node >= 22.12):

```bash
npm install                  # node-pty is native, needs build tools
npm run dev                  # tsx server/index.ts, http://127.0.0.1:3210
npm run typecheck            # tsc --noEmit, then hooks/*.mjs, bin/*.mjs and scripts/*.mjs (tsconfig.scripts.json, checkJs)
npm run test:unit            # Jest (swc), tests/unit/*.test.ts
npx jest tests/unit/hooks.test.ts -t "should ..."   # single unit test
npm run test:integration     # Playwright, starts an isolated dev server on :3211 (500ms demo steps, no local .env, temp data dir, tests/fake-claude on PATH)
npx playwright test tests/integration/questions.spec.ts   # single spec
npm run build                # next build --webpack
npm run verify               # typecheck, unit, build, integration: the CI sequence in one command
```

CI (`.github/workflows/ci.yml`) runs typecheck, unit, build, integration. `npm run verify` takes about five and a half minutes, nearly all of it in the integration suite, so it is run once per push and not once per commit:

- While working, and before a commit: `npm run typecheck` and the unit tests the change concerns, the whole unit suite (30 s) when in doubt.
- Before a push: `npm run verify` once, on the tree that is pushed. When the diff only touches documentation, prompts (`agents/`, `commands/`, `skills/`, `contracts/`, `principles/`) or `hooks/`, the unit suite is enough: it is what reads them, and the integration suite does not.
- Run these yourself and report their real output, including when a subagent already said the work passes.
- After a change under `console/` or `bin/`, run `impl restart`, otherwise the running console still serves the old build.

`impl demo` (or the demo mode in the UI) replays a simulated run from `server/demo.ts` / `demo-data.ts` without touching any repo or GitLab. Integration tests lean on it. `/?demo=incident` plays a pilot that hands back with nothing next, `/?demo=batch` a batch of three invented tickets with one conflict (`DEMO_BATCH`, canned analysis, merge request merged by a timer).

## Architecture

Flow: a hook fires in the Claude Code session (PTY). `hooks/hooks.json` runs `hooks/emit.mjs`, which POSTs the event to the local server with `IMPL_RUN_ID`. `server/engine` translates the raw hook payload into `EngineEvent`s, `server/hooks.ts` applies them to the `RunSession` the hook names, and the WebSocket sends the new state to the React UI (`components/factory.tsx` shell, `run-rail.tsx` sidebar, `run-view.tsx` and panels).

Several runs go at once. Everything a run owns lives on its `RunSession`, not in module state. What stays at module level belongs to the factory: the runs already audited and the audit queue in `self-improvement.ts`, the fake pending improvement of the demo in `demo.ts`. Every client message and HTTP route that acts on a run names it by `runId`.

- `server/engine/` is **the only code that knows the driven agent is Claude Code**: binary, hook vocabulary, transcript JSONL format, how to submit input, `.claude/tasks` path, `hookSpecificOutput`, and the headless scheduling call. `startSchedule` spawns `claude -p --setting-sources project,local --model sonnet --permission-mode dontAsk` (the user's settings stay out, a personal hook that rewrites a command would make it a refused one) with a fixed `--allowedTools` list on `/implementation-factory:schedule <input> <output>`, in the main checkout, without the hook variables and with `IMPL_SCHEDULE_OUTPUT` naming its output file (the list matches a command by its first words, the guard decides what each call may do), killed after `timeoutMs`; it returns `{ finished, kill }` and reports nothing while it runs. Nothing above it may import `node-pty` or read `hook_event_name`, and nothing does. The boundary is not complete for the rest: the `hookSpecificOutput` shape is typed in `server/types.ts` (`HookOutput`), `domain.ts` tests the tool name `Bash` and spells `.claude/worktrees`, the default of `IMPL_WORKTREE_COPY_FILES` names `.claude/settings.local.json`, and several messages write "Claude Code" where `engine.label` exists. Contract in `engine/types.ts`, rationale and the list of these leaks in `engine/README.md`. Keep new agent-specific logic in the engine.
- Guard: `hooks/guard.mjs` (`guardDecision`), called first by `emit.mjs`, refuses six kinds of `PreToolUse` call during a run of the workflow (`IMPL_RUN_ID` set or `workflow-state.json` present): a workflow agent under its bare name, a `developer` given a model override other than `sonnet` (its declared model) or `opus` (passed by the pilot for a task the plan sizes `L`), a reviewer started while a plan task has no developer report, a `git commit` or a `glab` or `gh` publication carrying a session trailer or link, a publication (those, plus a `glab api` or `gh api` call that writes) whose command or a text file it sends shows a credential (`SECRETS`: token shapes, JWT, private key, bearer; the refusal names the kind and the line, never the value), and a git command that destroys work (`reset --hard`, `clean -f`, a whole-tree checkout or restore, a bare forced push, `worktree prune`, the removal of a run worktree, plus a stash and a deleted or overwritten branch in a linked worktree). The git rules read the commands typed on the line (`shellCommands`), not what a quoted string or a script runs; git is found anywhere among the words of a command (behind `then`, `sudo`, `xargs`, an absolute path), a redirection glued to an argument is dropped, and a path that is the current directory, one above it or a pattern matching everything counts as the whole tree. The headless judge of an improvement branch has its own too (`judgeRefusal`, applied when `IMPL_JUDGE_OUTPUT` is set): `Write` to its verdict file only, no agent, no command. The headless scheduling session is not a run and has rules of its own (`scheduleRefusal`, applied when `IMPL_SCHEDULE_OUTPUT` is set, which `startSchedule` does): `Write` to its output file only, no other agent than `ticket-scheduler`, `glab` and `gh` only as `issue view` or an `api` call naming one issue or its links with no method, field or input option, `rm` on its output file only. The self-improvement and rebase sessions have no `IMPL_RUN_ID` and are not guarded. A refused call is not forwarded to the console, and a guard that cannot read what it checks lets the call through. A rule a tool input or a file listing decides goes there rather than in a prompt (`commands/improve.md`).
- Stop gate: `hooks/gate.mjs`, called by `emit.mjs` after the guard. `gateObserve` notes, per `agent_id`, the files each agent passes to `Edit`, `Write`, `MultiEdit` or `NotebookEdit` and which gated agents are alive, and fingerprints the changed paths of the tree when a gated agent starts alone (`git status` plus `hash-object`); at its stop, the paths whose content moved since are its edits too (`treeChanges`), since agents mostly edit through the shell. No fingerprint is kept while a peer works or once one starts, and a commit made in between voids it (state in the system's temporary directory, per session, `IMPL_GATE_STATE_DIR` in tests). `gateStop` judges the `SubagentStop` of `developer` and `senior-reviewer` during a run: per package the files belong to, the type-check of the package, then the lint and the related tests of those files (`gateSteps`, Node packages only); documentation and YAML files open no check. A failure sends the agent back once (`decision: block`, the stop is then not forwarded to the console); the second stop always goes through, and so does the stop of an agent whose transcript ends on a `SubagentHandback` call, which would not resume (its lines carry `handedBack: true`). Every verdict is a line of `.claude/tasks/gate-log.jsonl` (`pass`, `fail`, `inconclusive` for type errors outside the agent's files while a peer edits, `skipped` for a check that could not run, `none`), which the pilot and the review orchestrator read instead of the report; a check that was started carries its duration in `ms`. It fails open, and `IMPL_STOP_GATE=off` disables it. Rationale in `docs/engineering-workflow.md`, "The stop gate".
- Blocking questions: the `PreToolUse` hook on `AskUserQuestion` (timeout 3600s) waits for the UI answer, which returns as `updatedInput`. Claude Code replays the hook with answers; the engine ignores that second pass.
- Folder trust dialog: it is drawn before any hook or transcript, so `engine/trust-prompt.ts` reads it off the PTY output (matcher on the text with escapes and blanks removed, sample of Claude Code 2.1.288 in `tests/unit/fixtures/trust-dialog.json`) and the engine emits `session.prompt` / `session.prompt.end` through `StartOptions.onEvent`. `server/session-prompt.ts` keeps it as `RunState.sessionPrompt`, a state of its own and not the question bridge: shown as a decision in the conversation, answered with `sessionPrompt.answer` (the engine types the keys, `EngineSession.answerPrompt`), dropped on the first hook, when the screen moves on, or at exit. Never answered automatically. The directory it names is the session's `cwd`, so the run worktree, not the checkout. A refusal ends the run `stopped` with its reason (`RunSession.endedBy`), not `failed` with a `lost_session` incident, and its worktree is settled by `settleRunWorktree` like that of any stopped run (kept with its reasons). The headless scheduling session has no terminal and is not watched for the dialog. An unrecognised wording shows nothing.
- `server/access.ts` + `server/hook-bridge.ts`: every HTTP request needs a `Host` naming the console, the WebSocket an `Origin` it served, `/api/hooks` the secret carried in `IMPL_HOOK_URL`, drawn at each start unless `IMPL_HOOK_TOKEN` sets it (the integration suite does, being the only caller that posts hooks without a session; set in a `.env`, it stops changing from one start to the next). `emit.mjs` retries once, then spools the event to `data/runs/<id>/hooks-spool.jsonl` (`IMPL_HOOK_SPOOL`), replayed before the next hook and on every monitor tick; `hookId` dedupes. Questions are never retried nor spooled.
- Run health: `server/run-health.ts` (pure `evaluateRunHealth`, injected clock and policy) reads `RunSession.signals` (pilot turn end, tool calls paired by `toolUseId`, subagent vs pilot, background calls, notification causes) and `workflow-state.json` (`server/workflow-state.ts`), `server/run-incidents.ts` keeps incidents (fingerprint dedupe, resolution on the lifting event, action checks, archive normalisation), `server/run-monitor.ts` is the single scheduler the registry owns (tick + `session.signal()`, serialised per run with incident actions). A wait on the user is dated from its question (`PendingQuestion.askedAt`, `HealthInput.waitingSince`), not from the evaluation. Silence alone is only `suspected_stall`; a mid-workflow `turn.end` no longer sets `attention` by itself, and an exit before a result is `failed` with a `lost_session` incident. An agent that ends without a file its contract requires, with nobody taking over, raises an incident: `planner-output.json` for `ticket-planner`, `qa-report.md`, `qa-evidence.json` and `qa-plan.md` for `qa-reviewer`, `designer-review.md`, `design-evidence.json` and `design-inventory.md` for `designer-reviewer`, `review-summary.md` for `review-orchestrator` (`PRODUCER_CONTRACTS`). Actions go through `incident.action` (revision + requestId, decision persisted before the effect). Runs left with an open incident or a kept worktree are read back by `server/run-archive.ts` and served on `/api/archive/*`, never registered.
- `server/domain.ts`: pure logic, no FS/agent. Prefer putting logic here or in `engine/` so it is unit-testable.
- Review order: `RunSession.artifactArrived` records the first time each document is seen in `RunState.artifactArrivals` (called from `server/artifacts.ts`). `reviewPlanNotes` in `domain.ts` turns these times into `RunState.reviewNotes`, one note when `qa-plan.md` did not arrive before `qa-report.md`, or `design-inventory.md` before `designer-review.md`. A note is a remark shown in the evidence tab and changes no verdict. `phaseForArtifact` ignores both plan files, so they never open the next step.
- Phase: the step the pilot declares in `workflow-state.json` is the phase (`declaredPhase` in `domain.ts`, applied in `readWorkflowState`, never going back). What a document, an agent start or a command points at (`phaseForArtifact`, `phaseForAgent`) goes through `RunSession.inferPhase` and moves `RunState.phase` only while no step is declared: a document says which step wrote it, not which one is running. `RunSession.inferredPhase` keeps that reading for `closeWorkflowIfDone`, which still ends a run that stopped declaring. A step the pilot skips or never declares has no entry in `phaseArrivals`.
- `server/run-session.ts`: one run and everything it owns (state, archive, engine session, terminal buffer, artifact and transcript watchers, pending-question bridge, demo timers), with `activity()`/`publish()`. `persist()` writes `run.json` one write at a time: what changed during a write is one more write of the state as it then stands, and the promise holds until nothing is left to write. `registry.publishSnapshot()` sends the list of runs only when it differs from the last one sent.
- `server/registry.ts`: every run the console holds plus the launch queue (`data/queue.json`, restored on boot). A launch is resolved to the main checkout first (`mainCheckout`: a path inside a linked worktree names the same repository). Enforces one run per (repository, ticket) (`runLockKey`, on `ticketIdentity`: one identity for the `/-/issues/` and `/-/work_items/` addresses of a ticket, whatever the case of the host and the project, without query or fragment; held while `runHoldsRepository`: in progress or session still open) and `IMPL_MAX_CONCURRENT_RUNS`, counted on the runs whose workflow still works (`runTakesSlot`): a finished run frees its slot at once, its open session keeps only the ticket, and is closed when a launch waits on that ticket (`sessionsToReleaseForQueue`). A launch that hits either is queued with its reason, and the queue is drained (`drain`) whenever a run lets go, an analysis answers, a merge request is merged or the user acts on the queue. Several tickets of one repository run in parallel, unless the schedule below keeps them apart. The registry also owns the schedule state (`tickets`, `edges`, `watches`), the per-repository analysis chains and the `MergeWatcher`. `start` creates the run worktree before the session; a failed `git worktree add` aborts the launch, never a fallback on the checkout.
- Batch intake: the launch form sends `batch.submit` as soon as its ticket field holds two URLs or more (`lib/ticket-urls.ts`, `parseTicketUrls`, shared by the form and the server). `server/ticket-source.ts` (`resolvePastedTickets`) is the only code that knows the batch was pasted, and the place a GitLab query source would go: it resolves every URL to its main checkout, or to the checkouts the page chose for it in `targets`, and refuses the whole batch when one URL is invalid. A ticket with no checkout and no target queues nothing: the server answers `batch.unresolved` and the form asks where its merge requests go (`components/target-picker.tsx`). Cross-project delivery: a ticket filed in a project without code goes to the checkouts the user chose, one run per repository (`resolveTargets`), for a single ticket too (one repository through `run.start`, several through `batch.submit`); `deliveryProjects` in `domain.ts` decides when the session gets `IMPL_DELIVERY_PROJECTS` (the run's project is not the ticket's, or there are several), which makes the merge request cite the full reference and, with several projects, close nothing. `registry.enqueueBatch` takes `ResolvedTicket[]`, drops the tickets already queued, held by a run or behind a watched merge request (`admitBatch`, same key as `runLockKey`), and queues the rest under one `batchId`.
- Ticket proposals: `server/ticket-proposals.ts` (`TicketProposals`, owned by the registry) reads the file an outside watcher keeps up to date, `data/ticket-proposals.json` or `IMPL_TICKET_PROPOSALS_FILE`, every `IMPL_PROPOSALS_POLL_MS` (default 5 s, not in `impl config`), format in `contracts/ticket-proposals.md`. The file is a snapshot of every ticket that matches the watcher's filter. The console never asks GitLab for tickets and the watcher never calls the console; with no file nothing is queued and nothing else changes. `readProposalSnapshot`, `openProposals` and `handledStillFound` in `domain.ts` are the pure part: a ticket the console already has (compared by address, a proposal has no checkout) or already handled is left alone, and a decision is forgotten once its ticket leaves the file (`data/ticket-proposals-handled.json`; when that file cannot be read it is renamed `*.unreadable-<time>` and the tickets listed at the first reading are taken as handled, none is queued). After every reading, the new tickets go to `registry.launchProposals` with no click: `resolveProposedTickets` resolves each one on its own and `enqueueBatch` queues the resolved ones as one batch, then they are recorded as handled, so a ticket cancelled from the queue is not queued again while it stays in the file. One that cannot be launched keeps its reason in memory (`TicketProposal.refusal`) and is not tried again until it leaves the file or the console restarts; nothing is launched nor refused while shutting down. `FactorySnapshot.proposals` carries the tickets not queued, `components/proposal-list.tsx` shows them under the queue with their reason, and `proposal.dismiss` records the decision, and `proposal.launch` (`issueUrl`, `repositories`) queues a refused ticket on the checkouts the user chose. An entry may carry `repositories` (project paths, `projectPath` in `domain.ts`), resolved through `checkoutOfProject`. The `baseBranch` a proposal may carry (`branchName` in `domain.ts` drops anything that is not a plain branch name) follows it as `QueuedRun.baseBranch` and `RunState.ticketBaseBranch` and reaches the session as `IMPL_TICKET_BASE_BRANCH`, which a stacked start overrides; the pilot then skips the base question when that branch exists.
- Batch analysis: `server/schedule-analysis.ts` (`analyseTickets`) writes `input.json` under `<scheduleRoot>/<id>/`, calls `engine.startSchedule` and judges the session by `output.json` alone, validated whole by `validateSchedule` against `contracts/schedule.md`. One session per repository per batch, serialised per repository (`analysisChains`), outside `IMPL_MAX_CONCURRENT_RUNS`, bounded by `IMPL_SCHEDULE_TIMEOUT_MINUTES` (default 5). Entries are `analysing` until it answers. No session for a single new ticket in a repository with no known prediction (see Forge links); a lone `run.start` beside known predictions is analysed too. A missing or refused file, a timeout, or a restart during the analysis (`INTERRUPTED_ANALYSIS`) records the tickets as `analysis: "failed"`. The next analysis of the repository sends the tickets still queued, running or awaiting merge whose analysis failed as tickets to predict, not as `known` (`failedTickets`), and replaces their stored prediction; if it fails too they stay `failed`, and no analysis is opened for them alone. `scheduleRoot` (`scheduleDirectory` in `domain.ts`) is `implementation-factory-<user>/schedule/` in the system's temporary directory, private to the user, when the data directory sits inside the plugin, because Claude Code refuses a session any write inside the directory of the plugin it loaded; a data directory outside the plugin (`IMPL_DATA_DIR`) keeps them under `schedule/`. The directory is removed once the answer is read, kept with `session.log` on a failure, and `scheduleRoot` is wiped on boot.
- Forge links: beside the session, `forgeEdges` in the registry reads the blocking links of every ticket being analysed (`fetchIssueLinks` in `server/ticket.ts`: one `glab api .../issues/<iid>/links` call, or the two `gh api .../dependencies/blocked_by|blocking` ones, no Claude session). `linkEdges` in `domain.ts` turns a link to another ticket the console has in the same repository (`repositoryTickets`: queued, held by a run or awaiting merge) into a `depends_on` edge, matched by host, project and number since GitLab writes one issue as `/-/issues/` and `/-/work_items/`, and `overlayEdges` puts it over the agent's edge for that pair. It is recorded when the session failed too. A single new ticket beside tickets with no prediction gets this reading alone: inside `launch`, before the run may start, so `run.start` still answers with the run, and for a batch of one through `scheduleAnalysis` with `predicted` false, shown as `analysing` while it lasts. Unreadable links give no edge. A link to a ticket the console does not have, or of another repository, holds nothing.
- Scheduler: pure, in `domain.ts`. `conflictBetween` keeps two tickets of one repository apart on an edge (`overlap`, `depends_on`), and a ticket whose analysis failed or whose confidence is `low` apart from every other ticket of its repository (`analysis_failed`, `low_confidence`); tickets of two repositories never conflict. `detail` is written for the ticket that waits: it says whether the failed analysis or the vague prediction is its own or the other ticket's. `describeQueue` gives each entry its reason, first match wins: `ticket` (a run on the same ticket), `slot` for a forced entry, `analysis`, `conflict` (a conflicting run in progress), `merge` or `merge_unknown` (the watched merge request of a finished one), `dependency` or `order` (a conflicting entry ahead in the queue), else `slot`. `startableEntries` returns the `slot` entries, up to the free slots; a held entry takes no slot and is stepped over. `priorityOrder` puts the first ticket of a `depends_on` edge ahead of the second.
- Merge watch: when a scheduled run ends with a merge request, `runEnded` records a `MergeWatch` and the conflicting entries wait for the merge. `server/merge-watch.ts` (`MergeWatcher`) polls only the watches that hold a queued entry (`heldWatches`), every `IMPL_MERGE_POLL_MS` (default 60 s, not in `impl config`), and has no timer otherwise. The check is `fetchMergeRequestStatus` in `server/ticket.ts`: one `glab api` call made by the Node server, or `gh api` for a pull request (`deliveryEndpoint` and `deliveryStatus` in `domain.ts`: GitHub says a merge with `merged`, its `state` being only `open` or `closed`). It opens no Claude session and costs no tokens. `mergeWatchStep`: `merged` or `closed` drops the watch and releases what it held, `opened` keeps holding, and a failed call is `unknown`, which holds too. A run that ends without a merge request releases its dependents at once. A watch nothing waits on is forgotten after a week.
- Queue overrides: `queue.force` sets `QueuedRun.forced`, after which only the ticket lock and the slots hold the entry. Mode `base` starts from the base branch. Mode `stacked` needs the branch of the blocking ticket (from its run or its watch) and passes it to the session as `IMPL_BASE_BRANCH`. `queue.move` reorders (a dependency still goes first), `queue.cancel` removes.
- Run worktree: `server/run-worktrees.ts` owns the lifecycle, `server/worktree.ts` the git calls, `domain.ts` the pure decisions (`runWorktreePath`, `isRunWorktreePath`, `worktreeProvisioning`, `worktreeRemoval`). Every ticket run works in `<repo>/.claude/worktrees/<run-id>`, detached at the checkout's HEAD, the directory excluded through the repository's `.git/info/exclude`. `provisionWorktree` copies the ignored dependency directories copy-on-write (`IMPL_WORKTREE_DEPENDENCY_DIRS`, default `node_modules`, matched by name at any depth), symlinks one when the copy fails, copies ignored config files (`IMPL_WORKTREE_COPY_FILES`, default `.env*,.claude/settings.local.json`), and copies the ignored entries at or under a relative `core.hooksPath` (husky's `.husky/_`, without which the first commit fails); a provisioning failure is only a warning in the activity feed. The session gets `IMPL_RUN_WORKTREE`, `IMPL_SOURCE_REPOSITORY`, `IMPL_SOURCE_BRANCH` (omitted on a detached HEAD) and `IMPL_WORKTREE_DEPENDENCIES` (`symlink` as soon as one directory is linked, else `clone`, omitted when none was brought over). `staleDependencies` (in `run-worktrees.ts`, pure part `lockedPackages` and `dependencyDrift`) compares each `node_modules` brought over with the `package-lock.json` beside it (top-level packages, optional ones and links aside); a mismatch is an `attention` activity and `IMPL_WORKTREE_DEPENDENCIES_STALE` for the session, whose pilot reinstalls before the first agent, and an unreadable lockfile is reported, never guessed. `RunState.cwd` is the worktree and `RunState.repository` the checkout (`sourceRepository` reads older archives), so `.claude/tasks` is the worktree's own: cleared, watched and snapshotted there, never in the checkout. Once the session is gone, `settleRunWorktree` removes the worktree only when the run is `completed` with a merge request that is not a draft, the workflow not blocked, the archive sync acknowledged (`archiveSyncedAt`), the tree clean and HEAD on a remote-tracking ref (local refs, no fetch). Otherwise `RunState.worktree` turns `kept` with the reasons in `detail`. A shutdown marks it `kept`, and `reconcileRunWorktrees` applies the same rules on boot, before the archive is listed. `removeWorktreeOnRequest` is refused while the session lives and answers `confirm` with the `risks` (uncommitted, unpushed) until the request comes back with `force`. Only a path directly under `.claude/worktrees/` is ever removed, the branch never. The demo has no worktree.
- `server/context.ts`: the open sockets with the run each one is subscribed to, `broadcast()` (list of runs, notices) vs `broadcastToViewers()` (one run's state and terminal). `reportFailure(what, subject)` is what a write or a reading nobody awaits ends with: a line in `server.log` each time, with the stack when there is one, and one notice per kind of failure every ten minutes. The process has its own `unhandledRejection` and `uncaughtException` handlers, which report and keep the console up. `isMissingFile` tells an absent file from an unreadable one: an unreadable `queue.json` or `review-findings.json` is renamed `*.unreadable-<time>` before the console starts from nothing. Every HTTP request goes through `route`, whose failure is answered 500 (400 for an address that does not decode); a hook the console fails to apply is answered 500, which `emit.mjs` retries then spools. On boot, non-terminal archived runs are reclassified `failed`.
- WebSocket protocol, from the page: `run.start`, `run.subscribe`, `run.stop`, `run.close`, `terminal.input`, `terminal.resize`, `instruction.send`, `question.answer`, `sessionPrompt.answer`, `feedback.submit`, `incident.action`, `selfImprovement.approve`, `selfImprovement.reject` and `selfImprovement.revert` (`worktreeName`), plus the ones detailed below. From the server: `factory` (summaries + queue + archived runs + watcher tickets not queued, to every page), `run` and `terminal.output` (to the pages that opened that run via `run.subscribe`), `notice` (factory-level events; those of the improvement loop, sent by `notice()` in `self-improvement.ts`, carry `dismissAfterMs` and close on their own after 5 s), `error`, `incident.result`, `worktree.result` and `batch.result` (answered to the page that asked). The client sends `worktree.remove` (`runId`, optional `force`) for a live or archived run and gets `worktree.result` back (`removed`, `confirm` with `risks`, or `refused`). ## Conventions

- Code, identifiers, comments, commit messages, READMEs and `docs/` in English. User-facing UI text in English: the documentation quotes interface labels as they appear on screen. The language of what the workflow writes (reports, questions, merge request text) is chosen by the `IMPL_LANGUAGE` setting (`en` by default, `fr` for French).
- UI styling and wording follow `brand/README.md` (tokens, type scale, components, tone). A screen that departs from it is fixed, or the brand book is updated in the same commit.
- Commits: conventional prefixes (`fix:`, `feat:`, `chore:`), subject describes the behavior change in plain words. `self-improvement: apply improvements from self-improvement-<id>` is reserved for the improvement loop.
- Server modules are ESM and import siblings with the `.js` suffix (Jest maps it back).
- Unit tests: `describe(...)` + `it("should ...")`, one file per responsibility.
- Every `agents/*.md`, `commands/*.md` and `skills/*/SKILL.md` needs YAML frontmatter with `name` and `description`, and a skill's `name` is its directory (enforced by `tests/unit/plugin-metadata.test.ts`).
- Workflow language: `IMPL_LANGUAGE` (`en` default, `fr`), read by `server/config.ts` as `workflowLanguage` and by the prompts through `contracts/language.md`. The interface is English whatever it says. The one place the server writes in it is `acceptance-summary.md`: `server/acceptance-text.ts` holds every coverage sentence in both languages, `deriveAcceptanceCoverage` takes `language`, the "Evidence" tab is fed the English view and `workflowSummary` in `acceptance-runtime.ts` derives the other one for the file the merge request quotes. File-parsing diagnostics are English in both. The templates of the contracts and recipes stay written in French; `contracts/language.md` gives their fixed English headings.
- `principles/engineering.md` holds the short common decision rules, `principles/test-quality.md` the test shapes that cannot fail (read only when a diff touches tests); `contracts/` holds schemas and policies, `contracts/run-worktree.md` among them: the rules every agent of a run follows in its worktree (main checkout never written, symlinked dependency directories, ports, worktree and branch left in place), written once and linked from the pilot, the agents and `collect-evidence`. A rule is stated by the file that owns it, and the others point to it rather than restate it. Agents explicitly read them through `${CLAUDE_PLUGIN_ROOT}` paths; this root CLAUDE.md is not runtime context for plugin users. Methods live in `skills/`, loaded conditionally. See `docs/engineering-workflow.md` for routing, independent review and artifact ownership.
- Developer `self-check` and independent `review-change` must remain separate. `collect-evidence` supplies execution mechanics, never the reviewer's scenario selection or verdict. Reviewer expectations are established before reading author conclusions: QA writes them to `qa-plan.md`, the design reviewer to `design-inventory.md`, and briefs pass author evidence by path only.
- The design review (`designer-reviewer`, file `agents/designer-reviewer-figma.md`, skill `figma-review`) runs on Sonnet at every tier. With a mockup (Figma frames or one attached to the ticket) it runs on any change visible in the UI, tier 0 included; with no mockup at all, only when the diff modifies a shared UI component or creates a screen or route (the pilot decides). QA gets a disposable worktree only when the diff touches test files. A QA verdict `INCONCLUSIVE` never exits as ready. A design verdict `INCONCLUSIVE` is reported as "design not verified" and does not block.
- Editing `commands/` or `agents/` changes the workflow prompts run against real tickets; `implement.md` and agents are tightly coupled to Claude Code tool names.
- After changing server code, a running `impl` must be restarted (`impl restart`), otherwise it serves a stale Next manifest (unstyled page).

## Code habits

Eight habits a code audit found behind several defects each. Rules to apply when writing and reviewing; nothing counts them.

- What an agent writes about itself is a claim. The delivery URL, the source of an evidence file, a QA mandate, a `confirms` link: the console decides from what it observes itself (the file's name, the forge's answer, a date compared with the agent's start) and turns a declaration that differs into a diagnostic. A value the agent declared never completes a run, opens a merge watch or relaxes a check on its own.
- A safety rule is decided by a tool input or an allow-list, never by a sentence in a prompt alone. A session that reads ticket text gets no tool that writes outside its output. A rule that reads shell text is tested on the shapes that go around it (a wrapper in front, an absolute path, a control keyword, a glued redirection), and each test asserts which rule refused.
- A failure is handled or shown. No `.catch(() => undefined)`, empty `catch` or `void promise`. A persisted file that cannot be read is not an absent one: only `ENOENT` means absent, anything else is kept aside and reported before the file is written again.
- Data from outside is validated, not cast: a file an agent, an outside watcher or an older version wrote, a forge answer, a WebSocket message. Parse to `unknown`, validate every entry, drop the faulty one with a diagnostic. A contract in `contracts/` and its validator are held together by a test, as `FINDING_CATEGORIES` is.
- One owner per piece of interface state. Which run is open has one source, the rest is derived from it. State that belongs to a run is keyed by its id, so it does not survive a switch to another run.
- The cost of an event does not grow with the state. A hook, a `publish`, a monitor tick or a broadcast does not read again or write again everything the run holds. A `GET` writes nothing and calls no forge.
- Identity goes through its helper: `ticketIdentity` and `runLockKey` for a ticket, `hostLiteral` for a host, an id for a question. Two raw strings are not compared, and values are not joined on a separator the data may contain. An environment variable left empty is an absent one.
- A test calls the code it names. It does not restate the rule on a local constant, and it does not pass by a check that sits in front of the one it claims to cover. An absence is asserted after the event that proves the step ran, never after a fixed wait.
