Claude Code plugin + local console

Inside the console

How the local console runs a ticket: the path of a hook, the questions, the run worktree, run health, the evidence chain and what stays on disk. Who does what and on which model is in the agent map; this page shows the machinery underneath.

The pieces

A Next.js page and a Node server on 127.0.0.1:3210, started by impl. The server spawns the real claude binary in a PTY, one session per run, and learns what it does through its hooks. No direct API call and no key. The forge is read with glab or gh by the server itself, without a Claude session. In every diagram, hover a node to see what it does.

01

The path of a hook

Each hook of the session runs emit.mjs. The guard and the stop gate decide first, inside the session, then the event is posted to the server, which turns it into an engine event, applies it to the run and pushes the new state to the pages that opened that run.

What the guard refusesA workflow agent under its bare name, a Dev on a model other than Sonnet or Opus, a reviewer started while a task has no report, a session trailer in a commit or a publication, a publication that shows a credential, a git command that destroys work.
What the stop gate runsPer package the edited files belong to: the type-check, then the lint and the related tests of those files. A failure sends the agent back once. Every verdict is a line of gate-log.jsonl.
Lost hooksemit.mjs retries once, then spools the event. The spool is replayed before the next hook and on every monitor tick, and hookId drops the duplicates.
Fails openA guard that cannot read what it checks lets the call through, and so does a gate that cannot run a check. IMPL_STOP_GATE=off disables the gate.
02

Questions and decisions

A question from the workflow blocks the session until the engineer answers in the console. The folder trust dialog Claude Code draws before any hook is read off the terminal and shown the same way, but it is never answered on the engineer's behalf.

03

The run worktree

Every ticket run works in a git worktree of its own, created before the session and settled after it. The main checkout is never touched, and a worktree that may still hold work is kept with its reasons.

What the worktree receivesThe ignored dependency directories (node_modules by default), copied copy-on-write or linked when the copy fails, the .env* files and .claude/settings.local.json, and the ignored git hooks helper (husky's .husky/_). Build outputs are not provided.
What the session is toldIMPL_RUN_WORKTREE, IMPL_SOURCE_REPOSITORY, IMPL_SOURCE_BRANCH, how the dependencies came over, and IMPL_WORKTREE_DEPENDENCIES_STALE when they lag behind the lockfile.
If the worktree cannot be createdThe launch is aborted. The server never falls back on the main checkout.
Shutdown and restartA shutdown marks the worktree kept; the same rules run again on boot. Only a path directly under .claude/worktrees/ is ever removed, and the branch never is.
04

Run health

The server does not read silence as a failure. It pairs the tool calls, tells the pilot from its subagents and reads the step the workflow declares, evaluates all of it at each tick and opens an incident only when a decision is needed. The decision on an incident is written before it takes effect.

Break attemptsA QA item of kind attempt that fails counts against its criterion; any other is listed under it and verifies nothing.

Coverage frozen at deliveryThe code is identified until the workflow's end is archived. A rebase or an edit made afterwards, outside a reopening, leaves the delivered coverage as it was.
06

What stays on disk

Everything the console keeps is under console/data/, ignored by git. It holds ticket content: it never goes into tracked files, commits or docs.

data/runs/<run-id>/run.json (the state, one write at a time), terminal.log, artifacts/ (the workflow documents), evidence/, metrics.json (tokens, durations, diff), gate-log.jsonl, hooks-spool.jsonl while hooks wait.
data/queue.jsonThe launch queue and the schedule: tickets, conflict edges and merge request watches. Written whole, then renamed.
data/repositories/<checkout>-<digest>/Per repository: runtime-recipe.md (how the app is started and driven) and review-findings.json (the defects the reviews keep finding), both handed to the next run.
data/ticket-proposals.jsonThe file the outside watcher writes, read every 5 seconds, and ticket-proposals-handled.json for the tickets already queued or dismissed.
Batch analysesIn implementation-harness-<user>/schedule/ of the system's temporary directory, removed once read, kept with session.log on a failure, wiped on boot.
Unreadable is not absentA persisted file that cannot be read is renamed *.unreadable-<time> and reported before the console starts from nothing.
