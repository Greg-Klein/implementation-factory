# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Two things in one repo:

1. **A Claude Code plugin** (`.claude-plugin/`, `commands/`, `agents/`, `hooks/`, `skills/`). `/implementation-harness:implement` drives a GitLab or GitHub ticket end to end (clarify, plan, implement, test, specialized reviews, MR or PR). The ticket URL decides the forge: `glab` and the `glab-gitlab-api` skill for GitLab, `gh` and the `gh-github-api` skill for GitHub, where the ticket status is never moved and review captures stay local. `improve` and `rebase` run the self-improvement loop on this repo itself; `review` is the review step. `schedule` is run headless by the console to compare the tickets of a batch (agent `ticket-scheduler`, files defined in `contracts/schedule.md`).
2. **A local console** (`console/`): a Next.js UI plus a Node server that spawns the real `claude` binary in a PTY (`claude --plugin-dir <this repo> "/implementation-harness:implement <ticket>"`), inside a git worktree of the target repository created for that run, and makes its progress, agents, questions and documents visible. No direct Anthropic API calls, no API key.

There is no desktop app. The console only runs from the checkout through `impl`, so a merged self-improvement lands in the code that serves it (plugin files on the next run, `console/` and `bin/` after `impl restart`, which the merge notice asks for).

`bin/implementation-harness` is the `impl` launcher (start/demo/restart/stop/status/config/improve). `bin/config.mjs` + `env-schema.mjs` + `env-file.mjs` implement `impl config` over a local `.env` (the shell environment wins over `.env`, which wins over the defaults, see `.env.example`).

## Commands

All from `console/` (Node >= 22):

```bash
npm install                  # node-pty is native, needs build tools
npm run dev                  # tsx server/index.ts, http://127.0.0.1:3210
npm run typecheck            # tsc --noEmit
npm run test:unit            # Jest (swc), tests/unit/*.test.ts
npx jest tests/unit/hooks.test.ts -t "should ..."   # single unit test
npm run test:integration     # Playwright, starts an isolated dev server on :3211 (500ms demo steps, no local .env, temp data dir, tests/fake-claude on PATH)
npx playwright test tests/integration/questions.spec.ts   # single spec
npm run build                # next build --webpack
npm run verify               # typecheck, unit, build, integration: the CI sequence in one command
```

CI (`.github/workflows/ci.yml`) runs typecheck, unit, build, integration. Before calling work done, and before any commit:

- Run `npm run verify` yourself and report its real output, including when a subagent already said the work passes.
- After a change under `console/` or `bin/`, run `impl restart`, otherwise the running console still serves the old build.
- After `git push` on `main`, run `gh run watch --exit-status` in the background and report the result. Do not end the turn on a red or unknown CI.

`impl demo` (or the demo mode in the UI) replays a simulated run from `server/demo.ts` / `demo-data.ts` without touching any repo or GitLab. Integration tests lean on it. `/?demo=incident` plays a pilot that hands back with nothing next, `/?demo=batch` a batch of three invented tickets with one conflict (`DEMO_BATCH`, canned analysis, merge request merged by a timer).

## Architecture

Flow: a hook fires in the Claude Code session (PTY). `hooks/hooks.json` runs `hooks/emit.mjs`, which POSTs the event to the local server with `IMPL_RUN_ID`. `server/engine` translates the raw hook payload into `EngineEvent`s, `server/hooks.ts` applies them to the `RunSession` the hook names, and the WebSocket sends the new state to the React UI (`components/harness.tsx` shell, `run-rail.tsx` sidebar, `run-view.tsx` and panels).

Several runs go at once. Nothing run-specific is module state any more. Everything a run owns lives on its `RunSession`, and every client message and HTTP route that acts on a run names it by `runId`.

- `server/engine/` is **the only code that knows the driven agent is Claude Code**: binary, hook vocabulary, transcript JSONL format, how to submit input, `.claude/tasks` path, `hookSpecificOutput`, and the headless scheduling call. `startSchedule` spawns `claude -p --setting-sources project,local --model sonnet --permission-mode dontAsk` (the user's settings stay out, a personal hook that rewrites a command would make it a refused one) with a fixed `--allowedTools` list on `/implementation-harness:schedule <input> <output>`, in the main checkout, without the hook variables, killed after `timeoutMs`; it returns `{ finished, kill }` and reports nothing while it runs. Nothing above it may import `node-pty` or read `hook_event_name`. Contract in `engine/types.ts`, rationale in `engine/README.md`. Keep new agent-specific logic there.
- Guard: `hooks/guard.mjs` (`guardDecision`), called first by `emit.mjs`, refuses four kinds of `PreToolUse` call during a run of the workflow (`IMPL_RUN_ID` set or `workflow-state.json` present): a workflow agent under its bare name, a reviewer started while a plan task has no developer report, a `git commit` or a `glab` or `gh` publication carrying a session trailer or link, and a git command that destroys work (`reset --hard`, `clean -f`, a whole-tree checkout or restore, a bare forced push, `worktree prune`, the removal of a run worktree, plus a stash and a deleted or overwritten branch in a linked worktree). The git rules read the commands typed on the line (`shellCommands`), not what a quoted string or a script runs. The self-improvement and rebase sessions have no `IMPL_RUN_ID` and are not guarded. A refused call is not forwarded to the console, and a guard that cannot read what it checks lets the call through. A rule a tool input or a file listing decides goes there rather than in a prompt (`commands/improve.md`).
- Blocking questions: the `PreToolUse` hook on `AskUserQuestion` (timeout 3600s) waits for the UI answer, which returns as `updatedInput`. Claude Code replays the hook with answers; the engine ignores that second pass.
- Folder trust dialog: it is drawn before any hook or transcript, so `engine/trust-prompt.ts` reads it off the PTY output (matcher on the text with escapes and blanks removed, sample of Claude Code 2.1.288 in `tests/unit/fixtures/trust-dialog.json`) and the engine emits `session.prompt` / `session.prompt.end` through `StartOptions.onEvent`. `server/session-prompt.ts` keeps it as `RunState.sessionPrompt`, a state of its own and not the question bridge: shown as a decision in the conversation, answered with `sessionPrompt.answer` (the engine types the keys, `EngineSession.answerPrompt`), dropped on the first hook, when the screen moves on, or at exit. Never answered automatically. The directory it names is the session's `cwd`, so the run worktree, not the checkout. A refusal ends the run `stopped` with its reason (`RunSession.endedBy`), not `failed` with a `lost_session` incident, and its worktree is settled by `settleRunWorktree` like that of any stopped run (kept with its reasons). The headless scheduling session has no terminal and is not watched for the dialog. An unrecognised wording shows nothing.
- `server/access.ts` + `server/hook-bridge.ts`: every HTTP request needs a `Host` naming the console, the WebSocket an `Origin` it served, `/api/hooks` the per-boot secret carried in `IMPL_HARNESS_HOOK_URL`. `emit.mjs` retries once, then spools the event to `data/runs/<id>/hooks-spool.jsonl` (`IMPL_HOOK_SPOOL`), replayed before the next hook and on every monitor tick; `hookId` dedupes. Questions are never retried nor spooled.
- Run health: `server/run-health.ts` (pure `evaluateRunHealth`, injected clock and policy) reads `RunSession.signals` (pilot turn end, tool calls paired by `toolUseId`, subagent vs pilot, background calls, notification causes) and `workflow-state.json` (`server/workflow-state.ts`), `server/run-incidents.ts` keeps incidents (fingerprint dedupe, resolution on the lifting event, action checks, archive normalisation), `server/run-monitor.ts` is the single scheduler the registry owns (tick + `session.signal()`, serialised per run with incident actions). Silence alone is only `suspected_stall`; a mid-workflow `turn.end` no longer sets `attention` by itself, and an exit before a result is `failed` with a `lost_session` incident. An agent that ends without a file its contract requires, with nobody taking over, raises an incident: `planner-output.json` for `ticket-planner`, `qa-report.md`, `qa-evidence.json` and `qa-plan.md` for `qa-reviewer`, `designer-review.md`, `design-evidence.json` and `design-inventory.md` for `designer-reviewer`, `review-summary.md` for `review-orchestrator` (`PRODUCER_CONTRACTS`). Actions go through `incident.action` (revision + requestId, decision persisted before the effect). Runs left with an open incident or a kept worktree are read back by `server/run-archive.ts` and served on `/api/archive/*`, never registered.
- `server/domain.ts`: pure logic, no FS/agent. Prefer putting logic here or in `engine/` so it is unit-testable.
- Review order: `RunSession.artifactArrived` records the first time each document is seen in `RunState.artifactArrivals` (called from `server/artifacts.ts`). `reviewPlanNotes` in `domain.ts` turns these times into `RunState.reviewNotes`, one note when `qa-plan.md` did not arrive before `qa-report.md`, or `design-inventory.md` before `designer-review.md`. A note is a remark shown in the evidence tab and changes no verdict. `phaseForArtifact` ignores both plan files, so they never open the next step.
- Phase: the step the pilot declares in `workflow-state.json` is the phase (`declaredPhase` in `domain.ts`, applied in `readWorkflowState`, never going back). What a document, an agent start or a command points at (`phaseForArtifact`, `phaseForAgent`) goes through `RunSession.inferPhase` and moves `RunState.phase` only while no step is declared: a document says which step wrote it, not which one is running. `RunSession.inferredPhase` keeps that reading for `closeWorkflowIfDone`, which still ends a run that stopped declaring. A step the pilot skips or never declares has no entry in `phaseArrivals`.
- `server/run-session.ts`: one run and everything it owns (state, archive, engine session, terminal buffer, artifact and transcript watchers, pending-question bridge, demo timers), with `activity()`/`publish()`.
- `server/registry.ts`: every run the console holds plus the launch queue (`data/queue.json`, restored on boot). A launch is resolved to the main checkout first (`mainCheckout`: a path inside a linked worktree names the same repository). Enforces one run per (repository, ticket) (`runLockKey`, ticket URL without query or fragment; held while `runHoldsRepository`: in progress or session still open) and `IMPL_MAX_CONCURRENT_RUNS`, counted on the runs whose workflow still works (`runTakesSlot`): a finished run frees its slot at once, its open session keeps only the ticket, and is closed when a launch waits on that ticket (`sessionsToReleaseForQueue`). A launch that hits either is queued with its reason, and the queue is drained (`drain`) whenever a run lets go, an analysis answers, a merge request is merged or the user acts on the queue. Several tickets of one repository run in parallel, unless the schedule below keeps them apart. The registry also owns the schedule state (`tickets`, `edges`, `watches`), the per-repository analysis chains and the `MergeWatcher`. `start` creates the run worktree before the session; a failed `git worktree add` aborts the launch, never a fallback on the checkout.
- Batch intake: the launch form sends `batch.submit` as soon as its ticket field holds two URLs or more (`lib/ticket-urls.ts`, `parseTicketUrls`, shared by the form and the server). `server/ticket-source.ts` (`resolvePastedTickets`) is the only code that knows the batch was pasted, and the place a GitLab query source would go: it resolves every URL to its main checkout and refuses the whole batch when one URL is invalid or has no checkout. `registry.enqueueBatch` takes `ResolvedTicket[]`, drops the tickets already queued, held by a run or behind a watched merge request (`admitBatch`, same key as `runLockKey`), and queues the rest under one `batchId`.
- Ticket proposals: `server/ticket-proposals.ts` (`TicketProposals`, owned by the registry) reads the file an outside watcher keeps up to date, `data/ticket-proposals.json` or `IMPL_TICKET_PROPOSALS_FILE`, every `IMPL_PROPOSALS_POLL_MS` (default 5 s, not in `impl config`), format in `contracts/ticket-proposals.md`. The file is a snapshot of every ticket that matches the watcher's filter. The console never asks GitLab for tickets and the watcher never calls the console; with no file nothing is queued and nothing else changes. `readProposalSnapshot`, `openProposals` and `handledStillFound` in `domain.ts` are the pure part: a ticket the console already has (compared by address, a proposal has no checkout) or already handled is left alone, and a decision is forgotten once its ticket leaves the file (`data/ticket-proposals-handled.json`). After every reading, the new tickets go to `registry.launchProposals` with no click: `resolveProposedTickets` resolves each one on its own and `enqueueBatch` queues the resolved ones as one batch, then they are recorded as handled, so a ticket cancelled from the queue is not queued again while it stays in the file. One that cannot be launched keeps its reason in memory (`TicketProposal.refusal`) and is not tried again until it leaves the file or the console restarts; nothing is launched nor refused while shutting down. `HarnessSnapshot.proposals` carries the tickets not queued, `components/proposal-list.tsx` shows them under the queue with their reason, and `proposal.dismiss` records the decision. The `baseBranch` a proposal may carry (`branchName` in `domain.ts` drops anything that is not a plain branch name) follows it as `QueuedRun.baseBranch` and `RunState.ticketBaseBranch` and reaches the session as `IMPL_TICKET_BASE_BRANCH`, which a stacked start overrides; the pilot then skips the base question when that branch exists.
- Batch analysis: `server/schedule-analysis.ts` (`analyseTickets`) writes `input.json` under `<scheduleRoot>/<id>/`, calls `engine.startSchedule` and judges the session by `output.json` alone, validated whole by `validateSchedule` against `contracts/schedule.md`. One session per repository per batch, serialised per repository (`analysisChains`), outside `IMPL_MAX_CONCURRENT_RUNS`, bounded by `IMPL_SCHEDULE_TIMEOUT_MINUTES` (default 5). Entries are `analysing` until it answers. No session for a single new ticket in a repository with no known prediction (see Forge links); a lone `run.start` beside known predictions is analysed too. A missing or refused file, a timeout, or a restart during the analysis (`INTERRUPTED_ANALYSIS`) records the tickets as `analysis: "failed"`. The next analysis of the repository sends the tickets still queued, running or awaiting merge whose analysis failed as tickets to predict, not as `known` (`failedTickets`), and replaces their stored prediction; if it fails too they stay `failed`, and no analysis is opened for them alone. `scheduleRoot` (`scheduleDirectory` in `domain.ts`) is `implementation-harness-<user>/schedule/` in the system's temporary directory, private to the user, when the data directory sits inside the plugin, because Claude Code refuses a session any write inside the directory of the plugin it loaded; a data directory outside the plugin (`IMPL_DATA_DIR`) keeps them under `schedule/`. The directory is removed once the answer is read, kept with `session.log` on a failure, and `scheduleRoot` is wiped on boot.
- Forge links: beside the session, `forgeEdges` in the registry reads the blocking links of every ticket being analysed (`fetchIssueLinks` in `server/ticket.ts`: one `glab api .../issues/<iid>/links` call, or the two `gh api .../dependencies/blocked_by|blocking` ones, no Claude session). `linkEdges` in `domain.ts` turns a link to another ticket the console has in the same repository (`repositoryTickets`: queued, held by a run or awaiting merge) into a `depends_on` edge, matched by host, project and number since GitLab writes one issue as `/-/issues/` and `/-/work_items/`, and `overlayEdges` puts it over the agent's edge for that pair. It is recorded when the session failed too. A single new ticket beside tickets with no prediction gets this reading alone: inside `launch`, before the run may start, so `run.start` still answers with the run, and for a batch of one through `scheduleAnalysis` with `predicted` false, shown as `analysing` while it lasts. Unreadable links give no edge. A link to a ticket the console does not have, or of another repository, holds nothing.
- Scheduler: pure, in `domain.ts`. `conflictBetween` keeps two tickets of one repository apart on an edge (`overlap`, `depends_on`), and a ticket whose analysis failed or whose confidence is `low` apart from every other ticket of its repository (`analysis_failed`, `low_confidence`); tickets of two repositories never conflict. `detail` is written for the ticket that waits: it says whether the failed analysis or the vague prediction is its own or the other ticket's. `describeQueue` gives each entry its reason, first match wins: `ticket` (a run on the same ticket), `slot` for a forced entry, `analysis`, `conflict` (a conflicting run in progress), `merge` or `merge_unknown` (the watched merge request of a finished one), `dependency` or `order` (a conflicting entry ahead in the queue), else `slot`. `startableEntries` returns the `slot` entries, up to the free slots; a held entry takes no slot and is stepped over. `priorityOrder` puts the first ticket of a `depends_on` edge ahead of the second.
- Merge watch: when a scheduled run ends with a merge request, `runEnded` records a `MergeWatch` and the conflicting entries wait for the merge. `server/merge-watch.ts` (`MergeWatcher`) polls only the watches that hold a queued entry (`heldWatches`), every `IMPL_MERGE_POLL_MS` (default 60 s, not in `impl config`), and has no timer otherwise. The check is `fetchMergeRequestStatus` in `server/ticket.ts`: one `glab api` call made by the Node server, or `gh api` for a pull request (`deliveryEndpoint` and `deliveryStatus` in `domain.ts`: GitHub says a merge with `merged`, its `state` being only `open` or `closed`). It opens no Claude session and costs no tokens. `mergeWatchStep`: `merged` or `closed` drops the watch and releases what it held, `opened` keeps holding, and a failed call is `unknown`, which holds too. A run that ends without a merge request releases its dependents at once. A watch nothing waits on is forgotten after a week.
- Queue overrides: `queue.force` sets `QueuedRun.forced`, after which only the ticket lock and the slots hold the entry. Mode `base` starts from the base branch. Mode `stacked` needs the branch of the blocking ticket (from its run or its watch) and passes it to the session as `IMPL_BASE_BRANCH`. `queue.move` reorders (a dependency still goes first), `queue.cancel` removes.
- Run worktree: `server/run-worktrees.ts` owns the lifecycle, `server/worktree.ts` the git calls, `domain.ts` the pure decisions (`runWorktreePath`, `isRunWorktreePath`, `worktreeProvisioning`, `worktreeRemoval`). Every ticket run works in `<repo>/.claude/worktrees/<run-id>`, detached at the checkout's HEAD, the directory excluded through the repository's `.git/info/exclude`. `provisionWorktree` copies the ignored dependency directories copy-on-write (`IMPL_WORKTREE_DEPENDENCY_DIRS`, default `node_modules`, matched by name at any depth), symlinks one when the copy fails, and copies ignored config files (`IMPL_WORKTREE_COPY_FILES`, default `.env*,.claude/settings.local.json`); a provisioning failure is only a warning in the activity feed. The session gets `IMPL_RUN_WORKTREE`, `IMPL_SOURCE_REPOSITORY`, `IMPL_SOURCE_BRANCH` (omitted on a detached HEAD) and `IMPL_WORKTREE_DEPENDENCIES` (`symlink` as soon as one directory is linked, else `clone`, omitted when none was brought over). `RunState.cwd` is the worktree and `RunState.repository` the checkout (`sourceRepository` reads older archives), so `.claude/tasks` is the worktree's own: cleared, watched and snapshotted there, never in the checkout. Once the session is gone, `settleRunWorktree` removes the worktree only when the run is `completed` with a merge request that is not a draft, the workflow not blocked, the archive sync acknowledged (`archiveSyncedAt`), the tree clean and HEAD on a remote-tracking ref (local refs, no fetch). Otherwise `RunState.worktree` turns `kept` with the reasons in `detail`. A shutdown marks it `kept`, and `reconcileRunWorktrees` applies the same rules on boot, before the archive is listed. `removeWorktreeOnRequest` is refused while the session lives and answers `confirm` with the `risks` (uncommitted, unpushed) until the request comes back with `force`. Only a path directly under `.claude/worktrees/` is ever removed, the branch never. The demo has no worktree.
- `server/context.ts`: the open sockets with the run each one is subscribed to, `broadcast()` (list of runs, notices) vs `broadcastToViewers()` (one run's state and terminal). On boot, non-terminal archived runs are reclassified `failed`.
- WebSocket protocol: `harness` (summaries + queue + archived runs + watcher tickets not queued, to every page), `run` and `terminal.output` (to the pages that opened that run via `run.subscribe`), `notice` (harness-level events), `error`, `incident.result`, `worktree.result` and `batch.result` (answered to the page that asked). The client sends `worktree.remove` (`runId`, optional `force`) for a live or archived run and gets `worktree.result` back (`removed`, `confirm` with `risks`, or `refused`). It sends `batch.submit` (`issueUrls`, optional `instruction` applied to every ticket) and gets `batch.result` back (`batchId`, `accepted`, `duplicates`), then `queue.force` (`queuedId`, `mode` `base` or `stacked`, optional `onto`), `queue.move` (`queuedId`, `before`, `null` for the end) and `queue.cancel`, which answer through the next `harness` snapshot. `proposal.dismiss` (`issueUrls`) answers the same way, a failure through `error`. `demo.start` takes `scenario` `workflow`, `incident` or `batch`. It sends `recipe.forget` (`repository`) and gets `recipe.result` back (`forgotten`). HTTP: `/api/runs`, `/api/runs/<id>`, `/api/metrics`, `/api/repositories/recipe?repository=`, `/api/artifacts?runId=&path=`, and read-only `/api/archive/runs/<id>`, `/api/archive/runs/<id>/acceptance`, `/api/archive/artifacts`.
- "Tracking" board: `planner-output.json` is parsed when archived (`plannedTasks`), the engine reads the plan task id out of a developer delegation (the `developer-report-<id>.md` suffix in the `Agent` prompt), `delegatedTasks` drops the ids whose report already exists (a brief cites earlier reports as reading material), `pairDelegation` binds it FIFO to the next `SubagentStart` of that type, and `planTaskBoard` derives each card's column and assignee (report present = done). Agents get a first name and photo in start order (`agentIdentity`, pictures in `public/avatars/`) and a role (`agentRole`).
- Acceptance evidence: the pilot writes `acceptance-criteria.json` (stable `AC<n>` ids), tasks carry `criterion_ids`, evidence files follow `contracts/evidence.md`. `server/acceptance.ts` (pure) derives each criterion's status (failed wins over blocked, then unverified, then verified, and stale, unversioned or unreplaced evidence never counts as verified) and renders the MR summary. A QA item with `kind: "attempt"` is a break attempt: a failing one counts against the criterion it cites, any other is listed under it (`AcceptanceCriterionView.attempts`) and verifies nothing. `qaVerdictConsistency` compares the `status` of the latest QA report with QA's own executed observations on the current code and returns `AcceptanceView.qa`, with a warning when `PASS` or `PASS_WITH_WARNINGS` is declared over a criterion QA did not observe; a focused pass answers only for the criteria in its root `mandate`. The warning also goes into the MR summary (`qaWarning`); `server/evidence-archive.ts` keeps every version and its captures under `data/runs/<id>/evidence/`; `server/acceptance-runtime.ts` ingests, identifies the code with `hooks/code-snapshot.mjs` (the same utility the workflow runs), writes `acceptance-summary.md` back to the task directory and answers the pre-cleanup `archive-sync-request.json`. The full view is `/api/runs/<id>/acceptance`; `RunState.acceptance` and `RunSummary.acceptance` carry figures only, including the QA verdict digest (`acceptance.qa`: status, `consistent`, number of unobserved criteria).
- Run metrics: `server/engine/usage.ts` reads the tokens from the transcripts Claude Code keeps (`engine.sessionUsage`): one call is written on several lines under one message id and counted once with its last figures, the pilot's file is `<project>/<session>.jsonl` and each subagent's `<session>/subagents/agent-<id>.jsonl`, with the `agent_id` the hooks carry. `server/run-metrics.ts` is pure: `trackTimeline` (called from `RunSession.publish`, the one place every state change passes) records the waits on the user in `RunState.userWaits` and the first arrival at each phase in `phaseArrivals`; `buildRunMetrics` turns the state, the usage and the diff into `RunMetrics`; `metricsBaseline` and `metricsFindings` compare a run to the delivered runs, of the same review tier once three share it, and say nothing below three. `server/run-metrics-runtime.ts` does the files and git: `recordRunMetrics` writes `data/runs/<id>/metrics.json` when the workflow ends and again when the session exits (before the worktree is settled, since the diff is read in it), `refreshUsage` keeps `RunState.usage` and `RunSummary.tokens` moving during the run (at most one reading every 5 s), `backfillRunMetrics` measures on boot the archived runs that have no final figures. A run records `harness` (console version and plugin commit) and `baseCommit` at launch. The diff is measured from the branch its merge request targets, read from the forge (`fetchMergeRequestTarget`, `diffBases`), since the pilot cuts its branch from the base it chose, not from the checkout's HEAD; without a merge request it falls back on the stacked branch, then `baseCommit`. The pilot declares its review tier as `reviewTier` in `workflow-state.json`, kept in `RunState.reviewTier`. The self-audit entry carries `metrics`, `baseline` and `findings`. `GET /api/metrics` serves every measured run, the live ones recomputed; `components/metrics-panel.tsx` is the table, opened from the rail. The plan sizes and the tier are the harness's own estimate, the diff is the fact: never grade a run on the first two alone. The demo has no transcript: `demoSessionUsage` derives figures from how far the run got.
- `server/artifacts.ts`: watches the run worktree's `.claude/` (restricted to `tasks/`, because the workflow deletes and recreates `tasks/`) and copies documents into the run archive. Only files written since run start count.
- Runtime recipe: `server/runtime-recipe.ts`. The pilot writes `.claude/tasks/runtime-recipe.md` (`contracts/runtime-recipe.md`: how the target app is started, reached and driven, no secret). `keepRuntimeRecipe`, called from `server/artifacts.ts`, copies every version to `data/repositories/<checkout>-<digest>/runtime-recipe.md` (`runtimeRecipeStore` in `domain.ts`), and `seedRuntimeRecipe` puts it back in the task directory at the next launch on that repository, with the stored file's date so the watcher does not archive it as a document of the new run. The demo keeps nothing. `GET /api/repositories/recipe?repository=<absolute path>` reads it (`readRuntimeRecipe`), and the page sends `recipe.forget` to drop it (`forgetRuntimeRecipe`), answered by `recipe.result`; `components/recipe-dialog.tsx` is the window, opened from the "Repository" line of a run and from the launch form.
- `server/transcript.ts`: tails the session transcript for the conversation panel (lags behind the terminal by design).
- `server/self-improvement.ts` + `worktree.ts`: feedback/self-audit storage, `self-improvement-*` worktrees of this repo (unrelated to the run worktrees above), auto-rebase on HEAD moves, merge simulation via `git merge-tree --write-tree`, `mergeNeedsRestart` flags a merge that touched `console/` or `bin/`, one improvement in flight at a time (autonomous audits are queued and launched one after another, so runs finishing together cannot each open a branch). Nothing is ever pushed or auto-merged; the UI merge button is the only promotion path.
- Forge: `lib/ticket-urls.ts` reads the forge off the shape of an address, never off its host (`parseTicketUrl`, `parseDeliveryUrl`: `/-/` is GitLab, `/<owner>/<repo>/issues|pull/<n>` is GitHub, a GitLab host is never read as GitHub), and `forgeWords` gives what the interface calls things, `MR !12` or `PR #12`. Internal names stay GitLab's on both forges (`mergeRequestUrl`, `delivery: "merge_request"`, `mr-description.md`): archives and `queue.json` are read by them. The stand-ins `tests/fake-claude/glab` and `gh` keep every suite away from a real forge.
- `server/repository.ts`: finds the checkout for a ticket, GitLab or GitHub, by scanning `IMPL_SEARCH_ROOTS` two levels deep and reading `.git/config`.
- `lib/`: client-side helpers (run-state derivation, conversation, notifications, sound). `lib/run-state.ts` holds the queue row labels (`queueReason`, `queueStatus`, `scheduleMark`, `queueGroups`); `components/queue-list.tsx` renders the queue by batch then repository, with the two overrides. A row is dragged among the rows of its `queueDragScope` (its repository within its batch, or the lone launches), `queueDropTarget` giving the `before` of the `queue.move`; the arrows remain for the keyboard.

Runtime data lives in `console/data/runs/<run-id>/` (`run.json`, `metrics.json`, `terminal.log`, `artifacts/`), and one runtime recipe per repository in `console/data/repositories/`. `data/queue.json` is `{ version: 2, queue, tickets, edges, watches }` (`storedQueue`, written whole then renamed); the bare array written before batches still loads (`restoreQueueFile`), and nothing simulated is written. The files of an analysis are in `<scheduleRoot>/<id>/`, outside the plugin (see Batch analysis). Gitignored and confidential (ticket content): never copy it into tracked files, commits or docs.

## Conventions

- Code, identifiers, comments, commit messages, READMEs and `docs/` in English. User-facing UI text in English: the documentation quotes interface labels as they appear on screen. The language of what the workflow writes (reports, questions, merge request text) is chosen by the `IMPL_LANGUAGE` setting (`en` by default, `fr` for French).
- UI styling and wording follow `brand/README.md` (tokens, type scale, components, tone). A screen that departs from it is fixed, or the brand book is updated in the same commit.
- Commits: conventional prefixes (`fix:`, `feat:`, `chore:`), subject describes the behavior change in plain words. `self-improvement: apply improvements from self-improvement-<id>` is reserved for the improvement loop.
- Server modules are ESM and import siblings with the `.js` suffix (Jest maps it back).
- Unit tests: `describe(...)` + `it("should ...")`, one file per responsibility.
- Every `agents/*.md`, `commands/*.md` and `skills/*/SKILL.md` needs YAML frontmatter with `name` and `description`, and a skill's `name` is its directory (enforced by `tests/unit/plugin-metadata.test.ts`).
- Workflow language: `IMPL_LANGUAGE` (`en` default, `fr`), read by `server/config.ts` as `workflowLanguage` and by the prompts through `contracts/language.md`. The interface is English whatever it says. The one place the server writes in it is `acceptance-summary.md`: `server/acceptance-text.ts` holds every coverage sentence in both languages, `deriveAcceptanceCoverage` takes `language`, the "Evidence" tab is fed the English view and `workflowSummary` in `acceptance-runtime.ts` derives the other one for the file the merge request quotes. File-parsing diagnostics are English in both. The templates of the contracts and recipes stay written in French; `contracts/language.md` gives their fixed English headings.
- `principles/engineering.md` holds the short common decision rules, `principles/test-quality.md` the test shapes that cannot fail (read only when a diff touches tests); `contracts/` holds schemas and policies. Agents explicitly read them through `${CLAUDE_PLUGIN_ROOT}` paths; this root CLAUDE.md is not runtime context for plugin users. Methods live in `skills/`, loaded conditionally. See `docs/engineering-workflow.md` for routing, independent review and artifact ownership.
- Developer `self-check` and independent `review-change` must remain separate. `collect-evidence` supplies execution mechanics, never the reviewer's scenario selection or verdict. Reviewer expectations are established before reading author conclusions: QA writes them to `qa-plan.md`, the design reviewer to `design-inventory.md`, and briefs pass author evidence by path only.
- The design review (`designer-reviewer`, file `agents/designer-reviewer-figma.md`, skill `figma-review`) runs on Sonnet at every tier. With Figma frames it runs on any change visible in the UI; without Figma, only when the diff modifies a shared UI component or creates a screen or route (the pilot decides). QA gets a disposable worktree only when the diff touches test files. A QA verdict `INCONCLUSIVE` never exits as ready. A design verdict `INCONCLUSIVE` is reported as "design not verified" and does not block.
- Editing `commands/` or `agents/` changes the workflow prompts run against real tickets; `implement.md` and agents are tightly coupled to Claude Code tool names.
- After changing server code, a running `impl` must be restarted (`impl restart`), otherwise it serves a stale Next manifest (unstyled page).
