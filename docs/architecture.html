Implementation Harness

How the harness works

A local console that starts the real claude binary on a GitLab or GitHub ticket and shows what it does. No direct API call and no key: everything goes through the Claude Code session and its hooks. The console's interface is in French, and its labels are quoted as they appear.

1. The path of a run

You paste the URL of a ticket, the server finds the repository, creates a git worktree for the run and opens a Claude Code session in it, in a PTY. The main checkout is not touched. Each hook of the session comes back to the server, which updates the state of the run and pushes it to the interface. A question from the workflow blocks the session until you answer.

run flow (hooks, events, state) question, answer or decision, your turn documents produced by a session plain sequence
What the worktree receivesThe dependency directories Git ignores, copied or linked from the main checkout, and the .env* files. Build outputs are not provided.
If the worktree cannot be createdThe run does not start. The server never falls back on the main checkout.
After the sessionRemoved when the run is over, the MR is open and not a draft, the evidence is archived, the tree is clean and the branch is pushed. Otherwise kept with its reason. The branch is never deleted.

2. The /implementation-harness:implement workflow

Ten steps, run by a pilot that delegates to specialised agents. The only interactive step is the second. Each step leaves files in .claude/tasks/, which the console archives and shows.

  1. 01

    Read the ticket

    The ticket and every linked document.

  2. 02 · your turn

    Questions

    The only interactive step. The pilot then writes the register of criteria, with stable identifiers AC1, AC2…

    acceptance-criteria.json
  3. 03

    Dedicated branch

    Created in the run worktree, from the chosen base branch.

  4. 04

    Plan and breakdown

    ticket-planner on a complex ticket, the pilot alone on a simple one. Each task cites its criteria.

    planner-output.json
  5. 05

    Implementation

    One task at a time, by developer agents, then their reports are merged and checked off against the plan.

    developer-report-<id>.md, dev-evidence.json
  6. 06

    Reachable app and measurements

    The change is measured in the running application, on frozen code.

    state.json, captures
  7. 07

    Challenge

    Independent reviews, sized from the diff (detail below).

    senior-review.md, qa-report.md, designer-review.md
  8. 08

    Merge request

    Description prepared from the evidence summary. Failed or unverified criteria stay visible in it.

    acceptance-summary.md
  9. 09

    Consolidated review

    One review comment posted on the MR, with the captures.

    review-summary.md (tier 2)
  10. 10

    Final report

    Summary in the terminal, end declared, archive synced, then cleanup.

    workflow-state.json

3. Run health

The server does not rely on silence. It reads precise signals, evaluates them at each tick and opens an incident when something needs a decision. An action on an incident is recorded before it is executed.

suspected_stallSilence alone is only a doubt. A turn that ends in the middle of the workflow is no longer enough to ask for your attention.
failed + lost_sessionThe session stops before declaring a result. The run is interrupted, which is not a workflow error.
Lost hooksemit.mjs retries once, then spools the event to hooks-spool.jsonl, replayed at the next hook and at each tick.

4. The self-improvement loop

The harness also works on its own repository, one improvement at a time. Nothing is pushed or merged on its own: the merge button of the interface is the only way to promote a change. A merge that touches console/ or bin/ needs an impl restart.

5. A batch of tickets

You paste several URLs at once, or you launch tickets an outside watcher proposed. For each repository, an analysis session predicts what each ticket would touch and links the ones that cannot run together. The server starts what conflicts with nothing, 3 runs at a time at most, and holds the others until the awaited MR is merged.

What the analysis costsOne Claude Code session on Sonnet per repository and per batch, 5 minutes at most by default. It takes none of the 3 slots.
The watch uses no tokensThe server calls glab api or gh api, only while a ticket waits for an MR or a PR. If the forge does not answer, the ticket stays held.
Failed or unreliable analysisMissing or refused file, timeout exceeded, ticket too vague: the tickets of that repository run one at a time.
OverrideFrom the base: the second MR will probably have to be reworked by hand. Stacked: the MR targets the other ticket's branch and is merged after it.
LimitTried once on a real GitLab project, with three tickets. The stacked start and the start from the base only ran against the stand-ins the tests use for claude and glab.

6. Tickets proposed by a watcher

The console does not ask the forge which tickets to take. An outside tool does, and the two share one file.

One file between the watcher and the console

  • The watcher looks for tickets, for example by label, assignee and status, and writes everything that matches to ticket-proposals.json. It opens no Claude session and uses no tokens.
  • The file sits in the console's data directory, console/data/ticket-proposals.json by default, or wherever IMPL_TICKET_PROPOSALS_FILE points. The console reads it again every 5 seconds (IMPL_PROPOSALS_POLL_MS), so a change the watcher writes shows without a restart.
  • The console reads the file and lists the tickets under « Proposés ». Nothing starts until you launch one. A ticket launched or dismissed is not proposed again while it stays in the file.
  • ticket-source.ts resolves a launched proposal to its checkout, as it does for a pasted URL, and the queue is the same. Without the file the console works as before.
  • Not started: launching proposed tickets without the user.
